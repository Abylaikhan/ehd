# Постановка задач на доработку модуля ОБМ ЕВГА
## Простановка статусов по витрине рисков 5-15а, формирование уведомлений и исходящих писем

**Система:** ОБМ ЕВГА (`10.58.57.39`, БД `obm_evga`, схема `public`)
**Версия:** 1.0 (черновик для согласования)
**Дата:** 02.09.2026

---

## 1. Назначение

Доработка обеспечивает полный цикл работы аудитора ДВГА с результатами онлайн-бюджетного мониторинга: от простановки статуса по записи витрины рисков `its_tb_5_15a` до формирования уведомления об устранении нарушения, его согласования, подписания, регистрации канцелярией и отправки объекту контроля через ЕСЕДО, с последующей фиксацией результата отработки.

## 2. Термины и сокращения

| Термин | Расшифровка |
|---|---|
| КВГА | Комитет внутреннего государственного аудита МФ РК |
| ДВГА | Департамент внутреннего государственного аудита по области (территориальный орган КВГА) |
| Витрина 5-15а | Таблица `public.its_tb_5_15a` — результаты расчёта профилей риска |
| Запись риска | Строка витрины 5-15а, соответствующая одному платежу в разрезе одного профиля риска |
| Уведомление | Документ «Уведомление об устранении нарушения», направляемый объекту контроля |
| Исходящее письмо | Документ канцелярии, которым уведомление направляется адресату |
| ГУ | Государственное учреждение — отправитель платежа (`its_tb_5_15a.gu`) |
| Адресат | Организация-получатель письма из справочника ЕСЕДО (`its_cli`) |
| ЕСЕДО | Единая система электронного документооборота государственных органов |

## 5. Этап 1. Публикация данных на витрине

**Исполнитель:** робот публикации. **Периодичность:** согласно регламенту расчёта профилей риска.

**Действия:**

1. Выполняется расчёт по каждому активному профилю риска (`its_risk_profile.query_text`).
2. Результат загружается в `its_tb_5_15a`.
3. При загрузке обязательно заполняются:
   - `its_risk_profile_id` — сработавший профиль риска;
   - `its_departments_id` — департамент ДВГА, которому принадлежит запись (определяется по региону/КАТО отправителя платежа). **Без заполнения этого поля запись не будет видна ни одному аудитору;**
   - `its_risk_status_id = 1` («В работе у ДВГА») — стартовый статус;
   - `gu`, `gu_bin`, `ppo_pp`, `paymentdate`, `iin`, `fm`, `nm`, `ft`, `la1`, `amount_part`, `sendername`, `god`, `mes`.

**Правило повторной публикации (обязательное).** Загрузка выполняется методом слияния по ключу `(ppo_pp, its_risk_profile_id)` — на него уже существует уникальный индекс `its_tb_5_15a_ppo_pp_idx`:

| Ситуация | Действие |
|---|---|
| Записи нет в витрине | INSERT со статусом 1 |
| Запись есть | UPDATE **только расчётных** полей (суммы, реквизиты платежа, данные ГБД ФЛ, признаки). Поля `its_risk_status_id`, `risk_status_note`, `its_activity_id`, `refund`, `amount_for_vozvrat`, `files`, `audit_resp`, ссылки на уведомление и исходящее **не изменяются** |
| Запись отсутствует в новом расчёте | Не удаляется. Проставляется признак неактуальности |

Полная перезагрузка витрины (`TRUNCATE`/`DELETE + INSERT`) **запрещена** — она уничтожит результаты работы аудиторов и разорвёт связи с отправленными уведомлениями.

## 6. Этап 2. Реестр рисков

**Исполнитель:** аудитор ДВГА.

### 6.1 Видимость данных

Аудитор видит только записи своего департамента:

```sql
where its_tb_5_15a.its_departments_id = <департамент текущего пользователя>
```

Департамент пользователя определяется по `users.its_departments_id`. Роль «Куратор КВГА» видит записи всех департаментов в режиме чтения.

### 6.2 Состав грида

№, Профиль риска, Код ГУ отправителя (`gu`), Наименование отправителя (`sendername`), Номер платежа (`ppo_pp`), Дата платежа (`paymentdate`), ИИН получателя (`iin`), ФИО получателя (`fm`, `nm`, `ft`), Карт-счет (`la1`), Сумма (`amount_part`), Статус (`its_risk_status.title`), Комментарий (`risk_status_note`), Уведомление (№ или «—»), Исходящее письмо (№ или «—»).

### 6.3 Фильтры

Профиль риска, статус, период (`god`/`mes`, диапазон `paymentdate`), код ГУ, наименование отправителя, ИИН, диапазон суммы, признак «включено в уведомление / не включено», номер уведомления.

### 6.4 Функции

- чекбоксы для множественного выбора, включая «выбрать все на странице» и «выбрать все по фильтру»;
- простановка статуса — одиночная и массовая;
- формирование уведомления по отмеченным записям;
- выгрузка отфильтрованного реестра в Excel;
- просмотр карточки записи с историей изменения статусов.

### 6.5 Ограничения

Расчётные поля витрины (реквизиты платежа, ИИН, ФИО, суммы) доступны **только для чтения**. Редактированию подлежат исключительно поля отработки: статус, комментарий, суммы возмещения, вложения, привязка к аудиторскому мероприятию.

## 7. Этап 3. Простановка статусов записи витрины

### 7.1 Справочник статусов

Из 12 записей `its_risk_status` в обороте находятся 8. Четыре записи (`in_work` id=3, `notification_received` id=5, `potential` id=10, `other` id=9) выведены из оборота — их `title` заменён на «-».

| id | code | Наименование | Кто проставляет |
|---|---|---|---|
| 1 | `high` | В работе у ДВГА | Система (стартовый) |
| 4 | `notification_sent` | Уведомление направлено | Система (автоматически) |
| 6 | `waiting_documents` | Ожидание документов (от ГУ) | Аудитор |
| 11 | `confirmed` | Подтверждено | Аудитор |
| 2 | `no_violations` | Не подтверждено | Аудитор |
| 7 | `partial_refund` | Подлежит возмещению | Аудитор |
| 8 | `full_refund` | Возмещено | Аудитор |
| 12 | `audit` | Аудит | Аудитор |

**Важно для разработки:**
- работать **по `id`**, не по `code` — семантика кодов разошлась с наименованиями (`high` = «В работе у ДВГА», `partial_refund` = «Подлежит возмещению»);
- выпадающий список статусов фильтруется по `in$trash is null`, а не по признаку `title = '-'` (см. п. 14.2 — доработка справочника).

### 7.2 Матрица переходов

| Из статуса | Разрешённые переходы | Условия |
|---|---|---|
| 1 «В работе у ДВГА» | → 4 (автоматически при регистрации исходящего)<br>→ 2 «Не подтверждено» | Переход в 2 без отправки уведомления допускается для заведомо ложных срабатываний. Обязателен `risk_status_note` |
| 4 «Уведомление направлено» | → 6, → 11, → 2 | По результатам ответа объекта контроля |
| 6 «Ожидание документов» | → 11, → 2 | |
| 11 «Подтверждено» | → 7, → 12 | |
| 7 «Подлежит возмещению» | → 8, → 12 | Обязателен `amount_for_vozvrat`, значение ≤ `amount_part` |
| 12 «Аудит» | → 8 | Обязателен `its_activity_id` |
| 2 «Не подтверждено» | терминальный | |
| 8 «Возмещено» | терминальный | Обязателен `refund`. Если `refund < amount_for_vozvrat` — переход отклоняется, запись остаётся в статусе 7 |

**Общие правила:**

1. Статус 4 вручную не выставляется и не снимается — только системой в момент регистрации исходящего письма канцелярией.
2. Из статусов 4 и 6 возврат в статус 1 невозможен: запись уже фигурирует в отправленном документе.
3. Любой переход, не указанный в матрице, блокируется с сообщением «Переход из статуса X в статус Y не предусмотрен».
4. Каждое изменение статуса фиксируется в журнале (см. п. 14.3).

### 7.3 Массовая простановка

1. Аудитор отмечает записи чекбоксами и выбирает статус и комментарий — они применяются ко всем отмеченным.
2. Массовая операция допустима только в пределах своего департамента.
3. Записи, для которых выбранный переход недопустим, **не обрабатываются**. По завершении выводится отчёт: «Обработано N записей, отклонено M» с перечнем отклонённых и причиной.
4. Операция выполняется в одной транзакции.

## 8. Этап 4. Формирование уведомления

**Исполнитель:** аудитор ДВГА. **Точка входа:** кнопка «Сформировать уведомление» в реестре.

### 8.1 Условия включения записи

- статус записи = 1 «В работе у ДВГА»;
- запись не входит ни в одно действующее уведомление;
- запись относится к департаменту текущего пользователя.

Записи, не удовлетворяющие условиям, в формирование не попадают и выводятся отдельным списком с указанием причины.

### 8.2 Группировка

Отмеченные записи автоматически группируются по коду ГУ отправителя (`its_tb_5_15a.gu`). **Каждая группа = отдельное уведомление.** Объединение записей разных ГУ в одно уведомление не допускается.

Экран группировки — таблица:

| Код ГУ | Наименование отправителя | Кол-во записей | Общая сумма | Адресат | Действие |
|---|---|---|---|---|---|
| 2617832 | КГУ «Школа-гимназия №…» | 12 | 4 608 645,00 | *выбрать из ЕСЕДО* | исключить |

Требования к экрану:

1. Адресат выбирается **вручную для каждой группы** из справочника организаций ЕСЕДО (`its_cli`) — поиск по наименованию и коду.
2. Кнопка «Создать» неактивна, пока хотя бы у одной группы не выбран адресат.
3. Любую группу можно исключить из формирования — её записи остаются в реестре в прежнем статусе.
4. Записи с незаполненным `gu` в группировку не попадают, выводятся отдельным блоком с ошибкой.

### 8.3 Создаваемые объекты

По каждой группе создаётся:

**`its_risk_notice`** — шапка уведомления:

| Поле | Значение |
|---|---|
| `its_departments_id` | Департамент аудитора |
| `created_by` | Аудитор (инициатор) |
| `notice_txt` | Текст из шаблона |
| `exec_due_time` | Срок исполнения — 10 рабочих дней с даты регистрации исходящего |
| Номер уведомления | Присваивается при отправке на согласование (п. 12) |
| Статус | «Проект создан» |

**`its_risk_notice_5_15a`** — снимок каждой строки группы. Копируются: `tb_5_15a_id`, `its_risk_profile_id`, `gu`, `gu_bin`, `ppo_pp`, `paymentdate`, `iin`, `fm`, `nm`, `ft`, `la1`, `amount_part`, `sendername`.

Снимок принципиален: при последующем пересчёте витрины состав и содержание отправленного документа не должны изменяться.

**`its_risk_notice_recepient`** — выбранный адресат (`its_cli_id`).

### 8.4 Замечание по модели данных

В `its_risk_notice_5_15a` присутствуют два внешних ключа на одну и ту же таблицу: `tb_5_15a` и `tb_5_15a_id`. В фактических данных заполняется только `tb_5_15a_id`. **Рабочим считать `tb_5_15a_id`**, поле `tb_5_15a` не заполнять и вынести в план технического долга на удаление.

## 9. Этап 5. Формирование PDF

Файл формируется автоматически, состав и вёрстка — строго по утверждённому образцу.

### 9.1 Структура файла

1. Уведомление на казахском языке
2. Приложение к уведомлению на казахском языке
3. Уведомление на русском языке
4. Приложение к уведомлению на русском языке

### 9.2 Постоянная часть (шаблон)

**Шапка:** герб и двуязычное наименование — «Қазақстан Республикасы Қаржы министрлігі Ішкі мемлекеттік аудит комитеті» / «Министерство финансов Республики Казахстан Комитет внутреннего государственного аудита». Фоновый водяной знак.

**Текст письма (русская версия):** «Онлайн бюджетным мониторингом идентифицированы **высокие риски** в расходной части бюджета по случаям, указанным в приложении к настоящему уведомлению. На момент уведомления наблюдаются **признаки неправомерного перечисления** на карт-счета физических лиц. С целью пресечения необоснованного использования бюджетных средств **рекомендуется самостоятельное устранение рисков** в срок не позднее 10 (десяти) рабочих дней. В противном случае будет рассмотрен вопрос о принятии **директивных мер реагирования.**»

Казахская версия — аналогично образцу. Текст редактируется только администратором.

**Подвал:**
```
ДВГА по <область> КВГА МФ РК,
Подписано: <должность подписанта> <ФИО подписанта>

Исп. <ФИО аудитора>, тел <телефон>, эл.адрес <email>
Уведомление №:<номер> от <дата>
```

### 9.3 Переменная часть

| Элемент документа | Источник данных |
|---|---|
| Адресат (наименование + код) | `its_risk_notice_recepient` → `its_cli` |
| № уведомления, дата | Шапка уведомления |
| Наименование департамента | `its_departments` |
| ФИО и должность подписанта | Строка маршрута «Согласование» — фактический сотрудник, подписавший уведомление |
| ФИО, телефон, e-mail исполнителя | Профиль аудитора (`users`) |

**Таблица приложения** (порядок и наименования колонок — по образцу):

| Колонка | Источник (`its_risk_notice_5_15a`) |
|---|---|
| № п/п | Порядковый номер строки |
| Код ГУ отправителя | `gu` |
| Номер платежа | `ppo_pp` |
| Дата платежа | `paymentdate`, формат ДД.ММ.ГГГГ |
| Фамилия / Имя / Отчество | `fm` / `nm` / `ft` |
| ИИН | `iin` |
| Карт-счет | `la1` |
| Сумма | `amount_part`, формат с двумя знаками после запятой |

Колонки «Риск» и «Профиль риска» в печатную форму **не выводятся** — профиль риска используется только внутри системы для фильтрации.

### 9.4 Правила генерации

1. Проект PDF формируется при создании уведомления и перегенерируется при каждом изменении состава строк.
2. **Финальный файл формируется после подписания** — до этого момента подписант в маршруте может быть изменён, и подвал документа изменится вместе с ним.
3. После регистрации исходящего файл фиксируется как неизменяемый.
4. Файл сохраняется в `files` (S3) и связывается с уведомлением через `its_risk_notice.file_pdf`.

## 10. Этап 6. Маршрут

Вкладка «Маршрут» карточки уведомления. Заполняется аудитором.

### 10.1 Настройка маршрута

| Вид задачи | Порядок | Тип | Ответственный | Как заполняется |
|---|---|---|---|---|
| Согласование | 1 | Обязательный | Сотрудник своего департамента — как правило руководитель или заместитель | Выбирается вручную |
| Создать исходящее | 2 | Обязательный | Инициатор уведомления | Подставляется автоматически, доступен для замены |

Правила:

1. **Кнопка «Отправить на согласование» неактивна**, пока в маршруте не заполнены оба этапа: не указан хотя бы один согласующий и не назначен ответственный за создание исходящего. При попытке отправки выводится сообщение с указанием недостающего этапа.
2. Список ответственных ограничен сотрудниками **департамента текущего пользователя** — выбор сотрудника другого департамента невозможен.
3. Согласующих может быть несколько, обработка последовательная в порядке, заданном в маршруте.
4. Этап «Создать исходящее» при открытии вкладки предзаполняется инициатором уведомления. Пользователь может заменить ответственного на другого сотрудника своего департамента, но не может удалить сам этап.
5. **Канцелярия в маршрут уведомления не заводится.** Регистрация исходящего письма выполняется канцелярией на стороне ЕСЕДО после того, как исходящее создано и направлено туда.
6. Маршрут редактируется, пока уведомление в статусе «Проект создан» или «Отправлен на доработку».

### 10.2 Ход исполнения

Вторая часть вкладки, заполняется системой автоматически:

| Исполнитель | Дата | Тип задачи, номер задачи | Статус задачи | Действие |
|---|---|---|---|---|
| Умербаева Майрамкуль Ахатовна | 01.09.2026 15:31 | Согласование, № 362304 | Закрыта | Дата: 01.09.26 15:32 Действие: Согласовать |

Строка создаётся в момент постановки задачи (статус «Открыта») и закрывается при её отработке с фиксацией действия, даты и комментария.

## 11. Этап 7. Согласование, подписание, регистрация, отправка

### 11.1 Статусы уведомления

| Статус | Смысл |
|---|---|
| Проект создан | Создано, редактируется, номер не присвоен |
| На согласовании | Задача у согласующего |
| На подписании | Согласовано, задача у подписанта |
| Отправлен на доработку | Возвращено аудитору с комментарием |
| Исполнен | Исходящее зарегистрировано и отправлено адресату |

### 11.2 Сценарий

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1 | Аудитор | «Отправить на согласование» | Присваивается номер уведомления. Состав строк фиксируется. Статус → **На согласовании**. Задача согласующему (руководитель / заместитель) |
| 2 | Согласующий | Согласовать и подписать ЭЦП | Статус → **На подписании**. PDF перегенерируется с фактическим подписантом. Задача «Создать исходящее» возвращается инициатору |
| 2а | Согласующий | Вернуть на доработку с обязательным комментарием | Статус → **Отправлен на доработку**, задача аудитору |
| 3 | Аудитор | Доработать и повторно отправить | Возврат к шагу 1, **номер уведомления сохраняется** |
| 4 | Аудитор (инициатор) | Создать исходящее и направить в канцелярию через ЕСЕДО | Создаётся `its_out`, уведомление передано на регистрацию |
| 5 | Канцелярия (в ЕСЕДО) | Зарегистрировать исходящее: присвоить номер (формат `03-1-11/835`) и дату, отправить адресату | Номер и дата письма возвращаются в систему и сохраняются в `its_out`. Статус → **Исполнен** |

### 11.3 Действия системы в момент регистрации исходящего

Одной транзакцией:

1. В `its_risk_notice` проставляется ссылка на исходящее (`its_out_id`), номер и дата письма.
2. По всем записям витрины, входящим в уведомление, проставляется:
   - `its_risk_status_id = 4` («Уведомление направлено»);
   - ссылки на уведомление и исходящее письмо;
3. Рассчитывается контрольный срок: дата регистрации + 10 рабочих дней (по производственному календарю РК).
4. Записи в журнал изменения статусов с указанием источника «автоматически, регистрация исходящего №…».

### 11.4 Ограничения по редактированию

| Статус уведомления | Состав строк | Маршрут | Адресат | Удаление |
|---|---|---|---|---|
| Проект создан | ✔ | ✔ | ✔ | ✔ |
| Отправлен на доработку | ✔ | ✔ | ✔ | ✘ |
| На согласовании / На подписании / Исполнен | ✘ | ✘ | ✘ | ✘ |

## 12. Нумерация

### 12.1 Номер уведомления

Формат: `<код региона>/<год>/<порядковый номер>` → `11/2026/001097`, порядковый номер — 6 знаков с ведущими нулями.

**Код региона берётся из `its_regions.region_code`**, а не из `its_regions.code` и не из первых двух цифр КАТО. Проверка по фактическим данным: для Кызылординской области `code = 43`, `kato = 430000000`, **`region_code = 11`**, и именно `11` фигурирует в номере уведомления ДВГА по Кызылординской области. Связь: `its_departments.its_regions_id → its_regions.region_code`.

Правила выдачи:

1. Номер присваивается в момент нажатия «Отправить на согласование» — не при создании черновика, чтобы удалённые проекты не образовывали пропуски в нумерации.
2. Счётчик — `its_departments.notice_num` (последний использованный номер). Выдача выполняется в транзакции с блокировкой строки департамента: `select notice_num from its_departments where id = ? for update` → `notice_num + 1` → `update` → присвоение. Блокировка обязательна: без неё два аудитора, работающих одновременно, получат одинаковый номер.
3. **Счётчик сбрасывается в начале календарного года** — с 1 января нумерация начинается с 000001. Для этого в `its_departments` добавляется поле года последней выдачи (см. п. 14.1): если год в поле не равен текущему, счётчик обнуляется и год обновляется в той же транзакции.
4. При повторной отправке после доработки номер сохраняется, повторно не выдаётся.

### 12.2 Номер исходящего письма

Формат `03-1-11/835`. Присваивается **канцелярией при регистрации в ЕСЕДО**. Система его не генерирует, а принимает и сохраняет в `its_out` вместе с датой регистрации.

## 13. Этап 8. Отработка ответа объекта контроля

**Исполнитель:** аудитор ДВГА.

1. Реестр подсвечивает записи с истекающим и истёкшим контрольным сроком (10 рабочих дней).
2. По получении ответа ГУ аудитор переводит записи в соответствующий статус согласно матрице п. 7.2, прикладывает подтверждающие документы (`files`), фиксирует суммы возмещения.
3. Отдельный фильтр «Подтверждено без решения» — записи в статусе 11, по которым не принято решение о возмещении или передаче в аудит.
4. При передаче в аудит указывается мероприятие из `its_activity`.

### 14.1 Новые поля

```sql
-- Код и БИН ГУ-отправителя в снимке строк уведомления

alter table public.its_risk_notice_5_15a
    add column gu varchar(250),
    add column gu_bin varchar(20);

-- Год последней выдачи номера — для ежегодного сброса счётчика
alter table public.its_departments
    add column notice_num_year int4;
```

### 14.2 Доработка справочника статусов

```sql
-- Вывод из оборота неиспользуемых статусов
update public.its_risk_status
   set "in$trash" = 1
 where id in (3, 5, 9, 10);
```

Дополнительно требуется заполнить `title_kk` по всем действующим статусам — сейчас поле пустое во всех 12 записях, казахская версия интерфейса работать не будет. Значения предоставляются заказчиком.

### 14.3 Журнал изменения статусов

Поля `updated_by` / `updated_at` в `its_tb_5_15a` затираются при каждом обновлении и не обеспечивают прослеживаемость, необходимую для аудиторского контура. Создаётся отдельная таблица:

```sql
create table public.its_tb_5_15a_status_log (
    id                  bigserial primary key,
    "sys$uuid"          varchar(36) default uuid_generate_v4(),
    tb_5_15a_id         int8 not null references public.its_tb_5_15a(id),
    status_from_id      int8 references public.its_risk_status(id),
    status_to_id        int8 not null references public.its_risk_status(id),
    note                text,
    amount_for_vozvrat  numeric(20,2),
    refund              numeric(20,2),
    changed_by          int8 references public.users(id),
    changed_at          timestamptz not null default current_timestamp,
    change_source       varchar(50)   -- 'manual' | 'bulk' | 'system'
);
create index "its_tb_5_15a_status_log$tb_5_15a_id$idx"
    on public.its_tb_5_15a_status_log (tb_5_15a_id);
```

Запись в журнал выполняется при каждом изменении статуса, включая автоматические.

### 14.4 Защита от повторного включения записи в уведомление

```sql
-- Одна запись витрины не может входить более чем в одно уведомление
create unique index its_risk_notice_5_15a_tb_5_15a_id_uidx
    on public.its_risk_notice_5_15a (tb_5_15a_id);
```

Если бизнес допускает повторные уведомления по той же записи, индекс заменяется на частичный — с исключением аннулированных уведомлений. Требует подтверждения заказчика.

### 14.5 Уникальность номера уведомления

```sql
create unique index its_risk_notice_number_uidx
    on public.its_risk_notice (<поле номера>)
 where "in$trash" is null;
```

Конкретное поле определяется после уточнения структуры `its_risk_notice` (см. п. 16).

## 16. Открытые вопросы

Требуют уточнения до начала разработки:

1. **DDL таблицы `its_risk_notice`** — в предоставленных материалах отсутствует. В частности, не определено поле хранения статуса уведомления и поле номера уведомления. Если статус ведётся через `its_req.stat_id`, необходим DDL справочника статусов, на который ссылается `stat_id`.
2. **Таблицы маршрута и задач согласования** — где хранятся вид задачи, порядок, ответственный, номер задачи, статус и действия (данные вкладки «Маршрут» и «Ход исполнения»). Если это функциональность ЕСЕДО, требуется описание точек интеграции.
3. **DDL `its_cli`, `its_out`, `its_req`** и правила синхронизации справочника организаций с ЕСЕДО.
4. **Интеграция с ЕСЕДО:** документация API (справочник организаций, регистрация исходящего, отправка, получение статусов), адрес тестового контура, способ аутентификации.
5. **ЭЦП:** способ подписания (NCALayer или серверная подпись), объект подписи (PDF либо XML), место хранения подписи (`its_out.files_sign`, `second_sign`, `files.eds_exists`).
5а. **Момент подписания уведомления.** В настоящей редакции принято, что согласующий (руководитель / заместитель) одновременно подписывает документ ЭЦП на этапе «Согласование», отдельного этапа «Подписание» в маршруте нет. Требует подтверждения: если подписание выполняется отдельным действием или уже на стороне ЕСЕДО, п. 11.2 корректируется.
6. **Заполнение `its_tb_5_15a.its_departments_id`** при публикации — по какому признаку определяется департамент (КАТО отправителя, регион, `gu_bin`).
7. **Производственный календарь РК** — источник данных для расчёта 10 рабочих дней.
8. **Повторные уведомления** по одной и той же записи витрины — допустимы или нет (влияет на п. 14.4).
9. **Соответствие «один регион = один департамент ДВГА»** — если в одном регионе несколько департаментов, счётчики нумерации будут независимыми и номера в регионе задублируются.
10. Запись `its_regions` «Южно-Казахстанская область» (`region_code = 99`) выглядит устаревшей. Требуется исключить её из выбора либо пометить `in$trash = 1`.
