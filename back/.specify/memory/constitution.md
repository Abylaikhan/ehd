# Конституция бэкенда ЕХД

Неизменяемые принципы, которым обязаны соответствовать все `spec.md`, `plan.md`, `tasks.md` и код. Изменение конституции — только через `/constitution` с явным обоснованием и версией.

Версия: 1.0.0 · Действует с: 2026-08-20

---

## Принцип 1. Чистая архитектура и границы модулей

- Зависимости направлены внутрь: `transport → application/repository → domain`. `domain` не импортирует инфраструктуру.
- ЕХД — единый процесс с модулями `auth` и `reporter`. Между модулями **нет сетевых вызовов**: только через `auth/contract`-интерфейсы.
- У каждого модуля своя схема PostgreSQL и свой префикс маршрутов (`/api/v1/auth`, `/api/v1/reporter`).
- GORM-модели живут в `repository/`; доменные сущности в `domain/` остаются чистыми.

## Принцип 2. Фиксированный стек

- Go 1.26 · Fiber (HTTP) · GORM (PostgreSQL) · zap (логи) · viper (конфиг) · clickhouse-go (read-only источник).
- Замена любого из них — только через ADR в `specs/NNN-*/` и решение владельца. Молча вводить альтернативу запрещено.
- Конфигурация — только через окружение (viper). Секреты не хранятся в репозитории, docker-compose, коде и логах.

## Принцип 3. Безопасность Query Engine (из ТЗ, раздел 8)

- Запрещён `SELECT *`. Database/table/columns берутся только из published snapshot и сверяются со схемой.
- Значения фильтров — типизированные параметры; конкатенация пользовательских значений в SQL запрещена.
- Имена колонок — только из whitelist опубликованной конфигурации. Оператор — из серверной таблицы совместимости `source_type/operator`.
- Скрытая колонка (`visible=false`) не попадает в SELECT, JSON, логи и XLSX, даже если пользователь передал её имя (`REP-BR-007`).
- ClickHouse — только read-only SELECT. DDL/DML запрещены. Managed SQL — Phase 2, за feature flag, с AST-проверкой.

## Принцип 4. RBAC и Row-Level Security на сервере

- Права проверяются на backend при каждом запросе. Скрытие в UI не является механизмом безопасности.
- Row scope применяется по доверенному профилю пользователя; клиент не может передать/изменить коды региона и подразделения.
- Правила объединения: OR внутри измерения, AND между измерениями; NULL в колонке ограничения не возвращается обычному пользователю; согласованный fail-open при пустом профиле (`REP-FR`, раздел «Ограничение строк») — покрывается отдельным security-тестом.

## Принцип 5. Данные и миграции

- Sandbox: схемы и таблицы создаёт GORM AutoMigrate при старте.
- Production: контролируемые миграции до старта новой версии API (ТЗ). Переход фиксируется отдельной спекой.
- Пользовательские строки ClickHouse не копируются в PostgreSQL. Персональные поля шифруются на уровне приложения; ИИН имеет HMAC для поиска.

## Принцип 6. Наблюдаемость и надёжность

- Структурированные JSON-логи (zap) с `request_id`, `user_id`/hash, `view_id`, `duration`, `row_count`, `error_code`. Без секретов.
- `request_id` в каждом ответе; единый контракт ошибки `{request_id, error:{code,message,details}}`.
- Health: `/livez` без внешних зависимостей, `/readyz` с проверкой PG и CH.
- SIGTERM → graceful shutdown с закрытием активных соединений и отменой ClickHouse-запросов по context.

## Принцип 7. Тестирование — гейт готовности

- Unit: query builder (whitelist, все допустимые/запрещённые операторы, nullable, скрытые колонки), RBAC, оба режима RLS, slug/статусы, schema hash.
- Integration: репозитории и AutoMigrate на чистой БД; ClickHouse introspection и типизированные параметры; потоковый XLSX и лимиты.
- Обязательны негативные тесты безопасности до расширения функциональности.
- Каждое требование `REP-FR/BR` трассируется к тест-кейсу.

## Definition of Done (backend)

1. Код соответствует принципам 1–6; конфликтов с конституцией нет.
2. `go build ./...`, `go vet ./...`, `gofmt -l .` — чисто. `go test ./...` — зелёно, включая негативные тесты.
3. Каждая задача трассируется к `REP-FR/BR` и к затронутым файлам (через `graphify_impact`).
4. Реальный сценарий проверен на запущенном стеке; `/readyz` зелёный.
5. Graphify-граф обновлён (`graphify_build update=true`); OpenAPI и README актуальны.
