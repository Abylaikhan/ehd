# Спецификация: Reporter — Меню/Навигация (backend)

- **ID**: 007-reporter-menu
- **Статус**: draft
- **Требования ТЗ**: раздел «Реестр и карточка меню» (стр. 540–549); модель `menu_items`/`menu_item_roles` (стр. 923–961); раздел 10 (`/reporter/admin/menu-items`, `/reporter/navigation`); валидация дерева (стр. 1329, 1341, 1391)
- **UX-эталон**: легаси `angular_menu` (пункты, вложенность, роли, порядок, иконки)
- **Дата**: 2026-09-03

## 1. Цель и ценность
Дать администратору строить **дерево навигации Reporter**: раскладывать опубликованные витрины по пунктам левого меню с вложенностью, порядком, иконками и доступом по ролям. Конечный пользователь получает **разрешённое дерево** (`/reporter/navigation`), построенное backend по его ролям (роли ограничивают пункты; `public_access` — все аутентифицированные; циклы запрещены).

## 2. Пользовательские сценарии
- Администратор создаёт пункт меню: название, иконка, привязка к витрине (`data_view_id`) **или** раздел без привязки, родитель (вложенность до 3 уровней), порядок, роли/публичность, включён/выключен.
- Администратор редактирует/удаляет пункт; задаёт порядок.
- Пользователь получает дерево навигации: видны только разрешённые пункты (по ролям или public), с маршрутом на витрину по её текущему slug.
- Пустые разделы (без видимых детей и без привязки) в навигацию не попадают.

## 3. Функциональные требования
| ID | Требование | Источник ТЗ |

| FR-2 | Роли пункта — `menu_item_roles` (role_code); при public_access=false виден носителям роли; public_access=true — всем аутентифицированным (не anonymous) | стр. 955, 439 |

## 4. Контракты API
Админ (сессия admin):
- `GET    /reporter/admin/menu` — плоский реестр всех пунктов (+ роли, + slug привязки).
- `POST   /reporter/admin/menu` — создать пункт.
- `PATCH  /reporter/admin/menu/{id}` — обновить.
- `DELETE /reporter/admin/menu/{id}` — удалить (детей — каскадом/запретом при наличии).

Пользователь (сессия):
- `GET /reporter/navigation` — `{ items: MenuNode[] }`, где `MenuNode = { id, title, icon, to, children[] }` (`to` = `/reporter/{slug}` для привязки или пусто для раздела).

## 5. Сущности данных
`menu_items` (public): id, parent_id (uuid null), data_view_id (uuid null), name_ru, name_kk, icon_key, position, is_disabled, public_access, created_at, updated_at.
`menu_item_roles`: id, menu_item_id, role_code (uniq пара).

## 6. Нефункциональные ограничения
- Дерево валидируется на сервере (цикл/глубина); клиент не может «протолкнуть» цикл.
- Навигация фильтруется на сервере по ролям; фронт не расширяет доступ (Принцип 4).
- Меню в PostgreSQL; ClickHouse не задействован.

## 7. Критерии приёмки
- **AC-1**: создать раздел + вложенный пункт со ссылкой на витрину; `GET /admin/menu` возвращает оба с ролями/slug.
- **AC-2**: создание цикла (parent = потомок) → 422; глубина > 3 → 422.
- **AC-3**: `GET /navigation` под пользователем-с-ролью → видит только разрешённые пункты; под пользователем без роли и без public → пункт отсутствует; админ → всё.
- **AC-4**: пункт с public_access=true виден любому аутентифицированному; без сессии `/navigation` → 401.
- **AC-5**: раздел без видимых детей не попадает в навигацию; привязка резолвится в актуальный slug.
- **AC-6**: не-админ на `/admin/menu` → 403.

## 8. Вне объёма
- `placement` (несколько зон навигации), `process_code` (запуск бизнес-процессов), `route_name`/`code`, `revision`/If-Match — позже.
- Bulk `reorder` в одной транзакции (пока порядок через position в PATCH).
- Архив-политика для пунктов, привязанных к активной витрине (ENTITY_IN_USE) — позже.
- Казахская локализация UI (name_kk хранится).
