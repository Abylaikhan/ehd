# Спека 015 — ЭЦП согласующего при подписании уведомления (ОБМ ЕВГА)

Статус: принята (запрос пользователя, прод makeit.kz).
Связанные: 010-evga-approval (маршрут и согласование), 014-evga-esedo-send (серверная CMS ГОСТ — отдельный, неактивный контур).

## Проблема

Кнопка «Согласовать и подписать» (`POST /notices/:id/approve`) меняет только состояние маршрута:
закрывает шаг, фиксирует подписанта (`SetSigner`) и переводит заявку в «На подписании».
Криптографической подписи нет — ЭЦП в модуле используется лишь для входа (спека auth/eds).
По ТЗ §7 согласующий должен **подписать** уведомление, а не просто согласовать.

## Поведение (контракт)

### FR-1. Выдача challenge на подписание
`POST /api/v1/evga/notices/:id/approve/challenge` — для текущего пользователя и уведомления
выдаётся одноразовый случайный challenge (hex, 32 байта), TTL 5 минут.
Доступ: как у `approve` — только назначенный исполнитель открытого шага типа `approve`.

### FR-2. Подписание при согласовании
`POST /api/v1/evga/notices/:id/approve` принимает `{comment, challenge, signed_data}`.
При включённом режиме (FR-5) сервер:
1. потребляет challenge (одноразово, с проверкой владельца и уведомления) — иначе `EDS_CHALLENGE_INVALID`;
2. проверяет CMS через `eds.Verifier` (на проде — `ncanode`, RSA + ГОСТ РК) — иначе `EDS_VERIFICATION_FAILED`;
3. сверяет ИИН из сертификата с ИИН текущего пользователя — иначе `EDS_SIGNER_MISMATCH`
   (нельзя подписать чужим сертификатом).
Только после успешной проверки выполняется существующая логика закрытия шага.

### FR-3. Хранение подписи
Подпись (CMS) и отметка времени сохраняются в шаге маршрута
(`evga_notice_route_steps.sign_cms`, `signed_at`) — артефакт для аудита.
ИИН подписанта в открытом виде не сохраняется и не логируется (ПДн).

### FR-4. Отображение
`GET /notices/:id/route` отдаёт по шагу признак `signed` и `signed_at`
(сам CMS наружу не отдаётся). Фронт на шаге согласования запрашивает challenge,
подписывает его через NCALayer и отправляет в `approve`.

### FR-5. Рубильник
`EVGA_APPROVE_EDS` (bool, по умолчанию `false`). Подпись обязательна только при
`EVGA_APPROVE_EDS=true`. При `false` поведение прежнее (обратная совместимость,
локальный sandbox и автотесты не ломаются). На проде включается вместе с `EDS_MODE=ncanode`.

### FR-6. Возврат на доработку
`reject` подписи НЕ требует — отказ не является подписанным документом.

## Ограничения

- Это **подпись согласующего** (клиентский сертификат через NCALayer), а не серверная
  CMS ГОСТ юрлица для ЕСЭДО (спека 014) — контуры независимы.
- При `EDS_MODE=stub` проверка вырождается в stub-верификатор; боевой режим — `ncanode`.

## Приёмка

- AT-1: без `EVGA_APPROVE_EDS` approve работает как раньше (регресс).
- AT-2: с включённым режимом approve без `signed_data` → 422 `EDS_SIGNATURE_REQUIRED`.
- AT-3: повторное использование challenge → 422 `EDS_CHALLENGE_INVALID`.
- AT-4: подпись сертификатом другого лица → 422 `EDS_SIGNER_MISMATCH`.
- AT-5: валидная подпись → шаг закрыт, `signed_at` проставлен, статус «На подписании».
- AT-6: challenge может получить только исполнитель открытого шага (иначе 403).
