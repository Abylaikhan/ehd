# Спека 022 — ФИО участников маршрута, порядок адресатов, «Отправитель» = ДВГА

Статус: принята (13.10.2026). Основание — замечания аналитика п.2 и п.4 (`tz/obm-evga-5-15a/voprosy-analitiku-5.md`).
Связанные: 009-evga-notices, 010-evga-approval, 019-evga-grid-ux, 021-evga-prod-alignment.

Три независимых пункта, объединённые тем, что для каждого факты уже подтверждены
read-only подключением к боевой `obm_evga@10.58.57.39` — доп. согласования не требуются.

## FR-1. ФИО участников маршрута — из справочника `users_import`

**Проблема.** Имя сотрудника в выборе участников маршрута и в снапшоте шагов берётся из
`users.short_name` с откатом на `login`. В боевой БД `short_name` заполнен **у 1 из 715**
пользователей, поэтому аудитор видит в списке логины, а не ФИО.

**Факты (боевая БД).**

| Показатель | Значение |
|---|---|
| Пользователей с департаментом | 664 |
| Из них найдены в `users_import` по `usr_user_login = users.login` | **473** |
| Из найденных с заполненной фамилией | **473** |
| `users.short_name` заполнен | 1 из 715 |

**Требование.** Отображаемое имя сотрудника формируется как
`Фамилия Имя Отчество` из `users_import` (`usr_user_last_name`, `usr_user_first_name`,
`usr_user_father_name`) по связке `usr_user_login = users.login`.

- Нет записи в `users_import` или ФИО пусто → откат на `users.short_name`, затем на `users.login`
  (поведение не ухудшается ни для одного пользователя).
- Уникальность `usr_user_login` в `users_import` не гарантирована схемой → берётся одна запись.
- Поиск сотрудника ведётся **по отображаемому имени ИЛИ по логину**: аудитор ищет то ФИО,
  которое видит, но прежний поиск по логину/ИИН сохраняется — иначе у тех, кому ФИО
  подтянулось, поиск по логину перестал бы работать (регрессия).
- Правило применяется и к списку сотрудников департамента, и к снапшоту имён в шагах маршрута,
  т.е. уже сохранённые шаги маршрута продолжают показывать имя, зафиксированное при создании.

Схема `obm_evga` не меняется: `users_import` — существующая таблица платформы (read-only).

## FR-2. Ручной порядок адресатов уведомления

**Проблема.** С мультиадресатами (спека 018) порядок получателей равен порядку выбора
в автодополнении и не может быть изменён — только пересобрать список целиком.

**Факты (боевая БД).** Поле `its_risk_notice_recepient.nn` реально ведётся платформой:
`nn=1` — 494 записи, `nn=2` — 490, `nn=3` — 300, `nn=4` — 124. Порядок значим.

**Требование.** На экране формирования уведомлений порядок выбранных адресатов группы
изменяется вручную (перемещение адресата выше/ниже). Итоговый порядок передаётся на
сервер и сохраняется в `its_risk_notice_recepient.nn = 1..N` — он же определяет
последовательность в колонке «Адресат» списка и в PDF.

- Контракт API не меняется: `its_cli_ids` — упорядоченный массив, `nn` присваивается по позиции
  (уже реализовано спекой 018).
- Элементы управления доступны, когда у группы выбрано ≥2 адресатов; у исключённой группы — нет.

## FR-3. «Отправитель» в списке уведомлений — департамент ДВГА

**Проблема.** В списке уведомлений колонка «Отправитель» показывает наименование ГУ
(`its_risk_notice_5_15a.sendername`) — это **плательщик по платежу**, а не отправитель
уведомления. Отправителем уведомления является департамент ДВГА. В карточке уведомления
это уже так (`department`), в списке — нет.

**Требование.**

- Колонка «Отправитель» списка уведомлений содержит наименование департамента ДВГА
  (`its_departments.title`) и показывается всегда, независимо от области видимости
  (ранее департамент выводился только в режиме «все департаменты»).
- Наименование ГУ сохраняется отдельной колонкой «Наименование ГУ» рядом с «Код ГУ»
  — данные не теряются, меняется только семантика заголовка.
- Колоночный поиск (спека 019 FR-1) добавляется и для «Отправителя»: параметр `department`,
  подстрока, регистронезависимо, по наименованию департамента.

## Приёмка

- AT-1: в выборе участников маршрута сотрудник с записью в `users_import` отображается как ФИО.
- AT-2: сотрудник без записи в `users_import` отображается как раньше (short_name/login) — без «пустых» строк.
- AT-3: поиск по фрагменту фамилии находит сотрудника; поиск по фрагменту логина/ИИН продолжает работать.
- AT-4: при ≥2 адресатах доступно перемещение; созданное уведомление имеет `nn` в заданном порядке.
- AT-5: колонка «Адресат» списка перечисляет адресатов в заданном порядке.
- AT-6: в списке уведомлений «Отправитель» = департамент ДВГА, «Наименование ГУ» = ГУ-плательщик.
- AT-7: поиск по «Отправителю» фильтрует по наименованию департамента.
