## FR-1. Годовой сброс нумерации без `notice_num_year`

Запрос выдачи номера читал `d.notice_num_year`, которого в боевой БД нет, — на ней
`POST /notices/:id/submit` падал бы с ошибкой SQL, то есть отправка на согласование
не работала бы вовсе. Менять схему `obm_evga` нельзя: внешняя БД read-only.

Решение: год предыдущего номера извлекается **из самого номера** последнего уведомления
департамента (`<регион>/<год>/<NNNNNN>`), который читается в той же транзакции под
`for update of d`. Отдельное хранилище года не вводится — годовой сброс остаётся атомарным.

- `domain.YearFromNoticeNumber(docnum) *int32` — разбор года; нераспознанный номер → `nil`
  (трактуется как «другой год» → счёт с 1).
- `UPDATE its_departments SET notice_num = ?` — без `notice_num_year`.
- Правила нумерации не меняются: формат, блокировка строки департамента, сброс с 1 января.

## FR-2. Отмена каскада статуса при регистрации исходящего

Ранее при регистрации исходящего статус 4 «Уведомление направлено» проставлялся всем
записям того же `ppo_pp` по другим профилям. Это и создавало ограничение, описанное
в п.1 замечаний: записи уходили из статуса 1, и сформировать по ним уведомление было нельзя.

Теперь статус 4 получают **только записи снимка данного уведомления**. Записи других
профилей того же платежа остаются в «В работе у ДВГА» и отрабатываются отдельно.

## FR-3. Отмена каскада ручной смены статуса

Ранее ручная/массовая смена статуса применялась и к записям того же платежа по другим
профилям. Отменяется: в боевых данных 11% многопрофильных платежей уже имеют разные
статусы по профилям — аудиторы отрабатывают риски раздельно, и выравнивание им мешает.

Поле `Cascaded` в отчёте массовой операции сохраняется в контракте API и всегда равно 0.

## Ограничения

- Функция «автоматическое присвоение статусов повторяющимся рискам» (п.5 замечаний)
  этой спекой **не реализуется**: определение «повторяющегося риска» не согласовано
  (см. `tz/obm-evga-5-15a/voprosy-analitiku-5.md`, вопрос 1). Если под ним понимается
  не «другой профиль того же платежа», а иной ключ — потребуется отдельная спека.

## Приёмка

- AT-1: отправка на согласование выдаёт номер на БД без `notice_num_year`.
- AT-2: первый номер в новом году начинается с 1, в пределах года — инкремент.
- AT-3: повторная отправка после доработки сохраняет номер.
- AT-4: после регистрации исходящего записи других профилей того же платежа остаются в статусе 1.
- AT-5: по таким записям можно сформировать отдельное уведомление.
- AT-6: ручная смена статуса не меняет статус записей других профилей того же платежа.
