# Спецификация: ОБМ ЕВГА — отправка на согласование, маршрут, нумерация

- **ID**: 010-evga-approval
- **Статус**: implemented (backend)
- **Требования ТЗ**: EVGA-FR-050…057 (маршрут), EVGA-FR-060…064/068 (статусы, сценарий),
  EVGA-FR-070…074, EVGA-BR-020/021 (нумерация); ответы: В1/OQ-05а (согласование=подписание),
  №3-6 (маршруты платформы), АТ-09/09а/10/11/12/13/15
- **Дата**: 2026-09-08

## 1. Архитектурное решение (ADR)

Маршрут согласования ведётся в **БД ЕХД** (таблицы `evga_notice_route_step`, AutoMigrate),
а не в платформенных `tasks`/`task_approve_t`: процесс платформы движется BPMS-скриптами
(`its_create_out`, моделер id=2741), которые невозможно корректно повторить извне и опасно
задевать. В `obm_evga` пишется всё, что видно обеим системам: номер (`its_req.docnum`),
статус заявки (`its_req.stat_id`), подписант (`its_risk_notice.signer_id/signer_date`).
Участники маршрута — сотрудники департамента из `obm_evga.users`; исполнитель действия
сопоставляется по ИИН залогиненного пользователя ЕХД.

## 2. Функциональные требования

### Маршрут (EVGA-FR-050…057)

| ID | Требование |
|---|---|
| FR-1 | `GET /notices/:id/route` — этапы маршрута + ход исполнения (исполнитель, дата, тип, статус, действие/комментарий) |
| FR-2 | `PUT /notices/:id/route` `{approver_ids:[...], outgoing_user_id}` — редактирование только в статусах «Проект создан»/«Отправлен на доработку» (FR-056), только аудитором своего департамента/админом; согласующих ≥1, порядок = порядок списка (FR-053); ответственный за исходящее обязателен, по умолчанию инициатор (FR-054, предзаполнение на создании маршрута) |
| FR-3 | Участники — только сотрудники департамента уведомления: `GET /evga/users?q=` ищет в `obm_evga.users` по департаменту (FR-052); `"in$trash" is null`, `iin` заполнен |

### Отправка и сценарий (EVGA-FR-060…064)

| ID | Требование |
|---|---|
| FR-4 | `POST /notices/:id/submit` — только из статусов 1/12, только аудитор департамента/админ; маршрут обязан быть заполнен (иначе 422 `ROUTE_INCOMPLETE` с указанием недостающего этапа, AT-09); действия: присвоить номер (если нет), `its_req.stat_id=2` «На согласовании», открыть шаг первому согласующему. Повторная отправка после доработки: номер сохраняется (FR-064, AT-12), создаётся новый раунд шагов |
| FR-5 | `POST /notices/:id/approve {comment?}` — доступно пользователю, чей obm_evga-id (по ИИН) назначен в текущем открытом шаге согласования, при статусе 2. Согласование = подписание (В1): шаг закрывается с результатом «Согласовано»; если есть следующий согласующий — шаг ему; если последний — `stat_id=5` «На подписании», `its_risk_notice.signer_id=<согласующий>`, `signer_date=now`, открывается шаг «Создать исходящее» ответственному. Фактическая ЭЦП (CMS) — фаза 7 после выдачи серверного сертификата (пометка в ходе исполнения) |
| FR-6 | `POST /notices/:id/reject {comment}` — комментарий обязателен (422); закрывает открытый шаг с результатом «Возвращено на доработку», `stat_id=12`; маршрут снова редактируем |
| FR-7 | Ограничения §11.4: маршрут и удаление — по существующим правилам; submit/approve/reject вне допустимых статусов → 422 `NOTICE_NOT_EDITABLE`/`ROUTE_STATE_INVALID` |

### Нумерация (EVGA-FR-070…074)

| ID | Требование |
|---|---|
| FR-8 | Формат `<its_regions.region_code>/<год>/<NNNNNN>`; регион — через `its_departments.its_regions_id`; пустой `region_code` → 422 `NUMBERING_UNAVAILABLE` |
| FR-9 | Выдача в транзакции: `select ... from its_departments where id=? for update`; `notice_num_year ≠ текущий год` → счётчик с 1 и обновление года, иначе `notice_num+1` (AT-10/11); номер пишется в `its_req.docnum` |
| FR-10 | Номер присваивается только при первой отправке (не при создании проекта); при повторной отправке не перевыдаётся (AT-12) |

## 3. Хранение маршрута (БД ЕХД, AutoMigrate)

`evga_notice_route_step`: id, notice_id (obm_evga), round (раунд отправки), step_nn,
kind ('approve'|'outgoing'), assignee_obm_id, assignee_name, status ('draft'|'open'|'done'),
result ('approved'|'rejected'|''), comment, opened_at, closed_at, closed_by_obm_id,
created_at/updated_at. Шаблон маршрута (draft-строки round=0) редактируется PUT-ом;
при submit создаётся рабочий раунд.

## 4. Критерии приёмки

1. AT-09: submit без согласующего/ответственного → 422 с указанием недостающего этапа.
2. AT-09а: после создания маршрута этап «Создать исходящее» предзаполнен инициатором; `/evga/users` отдаёт только сотрудников департамента уведомления.
3. AT-11-подобный: первый номер департамента в году = `<регион>/<год>/000001`; следующий — 000002 (счётчик и год в `its_departments`).
4. AT-12: reject → доработка → повторный submit: номер не изменился, статус снова «На согласовании», новый раунд шагов.
5. Approve последним согласующим: статус «На подписании», `signer_id/signer_date` заполнены (AT-13 — подписант фактический), открыт шаг «Создать исходящее».
6. Approve чужим пользователем (не назначен в открытом шаге) → 403.
7. Reject без комментария → 422.
8. Маршрут не редактируется в статусе «На согласовании» (422), редактируется в 1/12.
9. Все пишущие операции — за `EVGA_WRITE_ENABLED`; куратор — только чтение маршрута.

## 5. Вне объёма

Реальная ЭЦП (CMS) подписания, PDF-перегенерация (фаза 5/7), создание `its_out` и ЕСЭДО
(фаза 7), каскад статуса 4 (фаза 7), UI (фронт-спека 008-evga-approval-ui).
