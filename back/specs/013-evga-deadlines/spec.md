# Спецификация: ОБМ ЕВГА — контрольные сроки и фильтр «Подтверждено без решения»

- **ID**: 013-evga-deadlines
- **Статус**: draft
- **Требования ТЗ**: EVGA-FR-080…083 (§13, `../tz/obm-evga-5-15a/09-otrabotka-otveta.md`)
- **Дата**: 2026-09-09

## 1. Контекст

Этап 8 «Отработка ответа объекта контроля». После регистрации исходящего (спека 011)
у записи появляется контрольный срок `its_out.exec_due_time` (= дата регистрации + 10
будних дней). Аудитор ждёт ответа ГУ и по нему переводит записи по матрице (спека 008).
Нужны два UX-инструмента для этого ожидания: **подсветка сроков** и **быстрый фильтр**
записей, застрявших в статусе «Подтверждено».

Что уже закрыто прошлыми фазами (в объёме — не переделываем):
- **FR-081** (перевод по матрице, суммы возмещения) — спека 008 (матрица §7.2,
  `amount_for_vozvrat`/`refund`). **Вложение подтверждающих документов** — ⛔ вне объёма:
  нет доступа к `files`/S3 платформы (Бауыржан).
- **FR-083** (мероприятие из `its_activity` при передаче в аудит) — спека 008 + справочник
  `Activities` (переход в статус 12; мероприятие опционально — ответ аналитика А2 от 07.09).

Новое в этой спеке: **FR-080** (подсветка) и **FR-082** (фильтр).

## 2. Решения (ADR / трактовки)

- **Источник срока**: `its_out.exec_due_time` (текстовая колонка `YYYY-MM-DD`, пишется в
  транзакции регистрации §11.3). Достаётся тем же боковым join'ом, что № уведомления/исходящего
  (`noticeLateral`: последний снимок → уведомление → исходящее).
- **Кому считать срок**: только записям, по которым ответ ещё ожидается — статусы **4**
  «Уведомление направлено» и **6** «Ожидание документов». Для решённых статусов (2/7/8/11/12)
  срок неактуален → состояние пустое. *(Трактовка — подтвердить у заказчика.)*
- **Состояния срока** (`deadline_state`), считаются на сервере от текущей даты:
  - `expired` — `exec_due_time < сегодня`;
  - `expiring` — `0 ≤ (exec_due_time − сегодня) ≤ EVGA_DEADLINE_WARN_DAYS` календарных дней;
  - `""` — срок не задан, запись вне статусов 4/6, либо до порога.
  - `EVGA_DEADLINE_WARN_DAYS` = **3** (ТЗ не задаёт окно «истекающий» → дефолт, подтвердить).
- **Каскадные соседи**: запись в статусе 4, попавшая туда каскадом по `ppo_pp` без включения
  в снимок уведомления, не имеет своего `noticeLateral` → срок пустой, не подсвечивается.
  Ограничение v1, зафиксировано; при необходимости — доработка по max(exec_due) того же платежа.
- **FR-082 «Подтверждено без решения»**: статус единственен, поэтому запись «в статусе 11 без
  решения о возмещении/передаче» ≡ **текущий статус = 11** (решение 7/12 уводит из 11).
  Реализуется отдельным именованным булевым фильтром (быстрый чекбокс), эквивалентным
  `its_risk_status_id = 11`; отдельный флаг — чтобы не смешивать с общим фильтром по статусу
  и дать один клик в UI.
- Подсветка — **только отображение**: FR-080 говорит «подсвечивает», не «фильтрует».
  На `COUNT`/пагинацию/экспорт не влияет.

## 3. Функциональные требования

| ID | Требование |
|---|---|
| FR-1 | Каждая запись реестра несёт `exec_due` (строка `YYYY-MM-DD` или пусто) и `deadline_state` (`""`/`expiring`/`expired`), вычисленные по §2. Поля добавляются в ответ `GET /registry` и `GET /registry/:id`. |
| FR-2 | `deadline_state` непусто только для статусов 4/6 при заданном `exec_due`; логика — чистая доменная функция, покрыта юнитами (граница сегодня, порог, вчера/завтра, пустой срок, чужой статус). |
| FR-3 | Фильтр `confirmed_no_decision=true` (query-параметр) добавляет условие `its_risk_status_id = 11`. Комбинируется с видимостью по департаменту и прочими фильтрами; влияет на список и `COUNT` одинаково. |
| FR-4 | Порог предупреждения — конфиг `EVGA_DEADLINE_WARN_DAYS` (env, дефолт 3). |
| FR-5 | Read-only инвариант сохраняется: только SELECT, `"in$trash" is null` везде. |
| FR-6 | Экспорт XLSX не обязан включать срок; поведение экспорта не меняется. |

## 4. Приёмка

1. Запись в статусе 4 с `exec_due` вчерашней датой → `deadline_state="expired"`.
2. Запись в статусе 4 с `exec_due` = сегодня+2 дня (при пороге 3) → `"expiring"`.
3. Запись в статусе 4 с `exec_due` = сегодня+30 дней → `""`.
4. Запись в статусе 11 с любым `exec_due` → `deadline_state=""` (вне 4/6).
5. `GET /registry?confirmed_no_decision=true` возвращает только записи статуса 11
   в пределах видимости; `total` согласован со списком.
6. Юниты доменной функции зелёные; `go build/vet/test ./...` зелёные; живой прогон на реплике.

## 5. Вне объёма

Вложение подтверждающих документов в записи (нет доступа к `files`/S3 — Бауыржан);
подсветка каскадных соседей без собственного снимка; передача в аудит как бизнес-действие
(мероприятие уже реализовано в спеке 008); календарь праздников РК (OQ-07 — срок в будних
днях считается при регистрации, здесь только сравнение календарных дат).
