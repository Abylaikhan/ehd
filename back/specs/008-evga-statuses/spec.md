# Спецификация: ОБМ ЕВГА — простановка статусов записей витрины 5-15а

- **ID**: 008-evga-statuses
- **Статус**: implemented (backend; прод в режиме чтения до согласования миграций)
- **Требования ТЗ**: EVGA-FR-015, EVGA-FR-018, EVGA-FR-020…024, EVGA-BR-010…015,
  EVGA-DB-001…005 — `../tz/obm-evga-5-15a/{03-statusy.md,10-izmeneniya-bd.md}`; AT-03…06
- **Дата**: 2026-09-06

## 1. Цель и ценность

Аудитор ДВГА отрабатывает записи витрины: переводит их по матрице статусов (одиночно и массово),
с обязательными атрибутами перехода и полной прослеживаемостью (журнал). Первый пишущий
функционал модуля — поэтому вводится явный режим записи.

## 2. Режим записи (критично)

- **FR-1.** Конфиг `EVGA_WRITE_ENABLED` (bool, по умолчанию `false`). При `false` модуль работает
  как в спеке 007 (строго read-only DSN), пишущие эндпоинты отвечают 403 `EVGA_READ_ONLY`
  «Модуль ОБМ ЕВГА работает в режиме чтения». Прод остаётся read-only до согласования
  миграций и пишущей учётки с заказчиком (указание владельца 06.09.2026).
- **FR-2.** При `true` DSN открывается без `default_transaction_read_only`; допустимые операции —
  только UPDATE полей отработки `its_tb_5_15a` (`its_risk_status_id`, `risk_status_note`,
  `amount_for_vozvrat`, `refund`, `its_activity_id`) и INSERT в `its_tb_5_15a_status_log`.
  Расчётные поля витрины не изменяются (EVGA-FR-019). DDL из кода запрещён.

## 3. Матрица переходов (EVGA-FR-020, работа по id — EVGA-BR-010)

| Из | Разрешено в | Условия входа в целевой статус |
|---|---|---|
| 1 «В работе у ДВГА» | 2 | → 2 всегда требует `note` |
| 4 «Уведомление направлено» | 6, 11, 2 | |
| 6 «Ожидание документов» | 11, 2 | |
| 11 «Подтверждено» | 7, 12 | → 7 требует `amount_for_vozvrat` > 0 и ≤ `amount_part` |
| 7 «Подлежит возмещению» | 8, 12 | → 12 требует `activity_id` |
| 12 «Аудит» | 8 | → 8 требует `refund` > 0; если `refund < amount_for_vozvrat` (когда та задана) — отказ, запись остаётся в текущем статусе (AT-05) |
| 2, 8 | — (терминальные) | |

- **FR-3.** Статус 4 недостижим вручную и не снимается вручную… кроме переходов 4→6/11/2 из
  матрицы (BR-012: выставляет 4 только система при регистрации исходящего — фаза 7,
  `change_source='system'`).
- **FR-4.** Любой переход вне матрицы → 422 `TRANSITION_NOT_ALLOWED`, сообщение
  «Переход из статуса X в статус Y не предусмотрен» (BR-014, AT-03).
- **FR-5.** Условия входа (`note` для 2, `amount_for_vozvrat` для 7, `activity_id` для 12,
  `refund` для 8) → 422 `TRANSITION_CONDITION_FAILED` с деталью, чего не хватает (AT-04/05).
- **FR-6.** Целевой статус должен существовать, быть действующим (`in$trash is null`,
  BR-011) и не равняться текущему.

## 4. Одиночная и массовая простановка

- **FR-7.** `POST /api/v1/evga/registry/:id/status` `{status_id, note?, amount_for_vozvrat?,
  refund?, activity_id?}` — роль `evga_auditor` (запись своего департамента) или админ;
  куратор — только чтение → 403 `ACCESS_DENIED`. Успех: обновлённая карточка.
- **FR-8.** `POST /api/v1/evga/registry/status/bulk` `{ids[], status_id, note?, …}` —
  до 1000 id за вызов. Семантика EVGA-FR-021…024: применяется ко всем отмеченным; записи
  с недопустимым переходом/условием НЕ обрабатываются; ответ-отчёт
  `{processed, rejected, rejections:[{id, reason}]}`; вся операция — одна транзакция
  (обновления валидных записей коммитятся вместе; отклонённые не мешают коммиту).
- **FR-9.** Блокировка строк: `SELECT … FOR UPDATE` выбранных записей в транзакции —
  два одновременных аудитора не потеряют обновления.
- **FR-10.** Атрибуты перехода пишутся в запись: `risk_status_note` (всегда при наличии),
  `amount_for_vozvrat` (при →7), `refund` (при →8), `its_activity_id` (при →12).

## 5. Журнал (EVGA-DB-003, BR-015)

- **FR-11.** Каждый успешный переход пишет строку `its_tb_5_15a_status_log`
  (status_from/to, note, суммы, `changed_by`, `change_source` = 'manual' | 'bulk').
  `changed_by` — id пользователя **obm_evga**, найденный по ИИН (тем же резолвом, что scope);
  для пользователя ЕХД без записи в obm_evga (например, админ) — NULL, колонка nullable.
- **FR-12.** `GET /api/v1/evga/registry/:id/history` — история переходов записи для карточки
  (EVGA-FR-018): дата, из→в (title), комментарий, суммы, кто (`users.fio`/логин из obm_evga),
  источник. Доступ — как к карточке.

## 6. Миграции (EVGA-DB-001…005)

- **FR-13.** SQL-скрипты в `back/migrations/evga/` (нумерованные, идемпотентные где возможно).
  Применение: **вручную** (psql), из кода не выполняются. Сейчас применяются только
  к dev-реплике; прод — после подтверждения заказчика (OQ-08 влияет на 004).
  Функционал статусов требует минимум 003 (журнал); отсутствие таблицы журнала при
  включённой записи — ошибка старта health-проверки не вызывает, но переходы вернут 503.

## 7. Критерии приёмки

1. AT-03: 4→1 → 422 `TRANSITION_NOT_ALLOWED` с текстом «Переход из статуса 4 в статус 1 не предусмотрен».
2. AT-04: →2 без note → 422 `TRANSITION_CONDITION_FAILED{field:risk_status_note}`.
3. AT-05: 7→8 с refund < amount_for_vozvrat → 422, запись осталась в 7, журнал пуст.
4. AT-06: bulk по N записям, из них M в недопустимом статусе → `{processed:N-M, rejected:M}` с причинами; обработанные изменены, отклонённые нет; всё в одной транзакции.
5. Каждый успешный переход виден в `GET /registry/:id/history` (from/to/кто/когда/источник).
6. Аудитор не может изменить запись чужого департамента (404), куратор — 403 на любую запись.
7. При `EVGA_WRITE_ENABLED=false` все пишущие эндпоинты → 403 `EVGA_READ_ONLY`; GET-эндпоинты работают как прежде.
8. Негативные юниты: полная таблица матрицы (все пары из×в), все условия входа.

## 8. Вне объёма

Автоматический статус 4 при регистрации исходящего (фаза 7); UI простановки статусов
(отдельная фронт-спека 006-evga-statuses-ui); применение миграций к проду; вложения (`files`);
фильтр «Подтверждено без решения» и подсветка сроков (фаза 8).
