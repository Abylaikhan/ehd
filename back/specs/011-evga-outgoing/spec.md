# Спецификация: ОБМ ЕВГА — исходящее письмо и регистрация

- **ID**: 011-evga-outgoing
- **Статус**: implemented (без отправки в ШЭП — ждёт учётку)
- **Требования ТЗ**: EVGA-FR-065…068 (§11.2 шаги 4–5, §11.3), EVGA-FR-067а (каскад по платежу),
  §12.2 (номер исходящего — принимаем, не генерируем), №3-5 (срок = +10 будних дней),
  №3-7 (извещения обрабатывает платформа — следим за `its_out` в БД); AT-14
- **Дата**: 2026-09-09

## 1. Границы

Реальная отправка в ШЭП/ЕСЭДО — НЕ здесь (нет учётки, вопрос у Бауыржана). Здесь:
создание `its_out` ответственным, реакция на регистрацию (номер/дата появляются в `its_out` —
их проставляет платформа по извещению `stateRegistered`, ответ №3-7) и вся транзакция §11.3.
Для теста и ручного сценария — админ-эндпоинт симуляции регистрации.

## 2. Функциональные требования

| ID | Требование |
|---|---|
| FR-1 | `POST /notices/:id/outgoing` — исполнитель открытого шага «Создать исходящее» (по ИИН) при статусе заявки 5 «На подписании». Действия одной операцией: создать `its_out` (`subject` = «Уведомление №<docnum>», `its_risk_notice_id`, `created_by`, `sender_cli_id` = организация департамента `its_departments.its_cli_id`), проставить `its_risk_notice.its_out_id`, закрыть шаг маршрута (result approved). Статус заявки не меняется (промежуточного статуса в данных прода нет; регистрация переведёт в 3) |
| FR-2 | Повторное создание исходящего для уведомления → 422 `ROUTE_STATE_INVALID` (у уведомления уже есть `its_out_id`) |
| FR-3 | **Регистрация** (внутренняя операция `Register`): по появлению `doc_num`+`doc_date` в `its_out` выполняется транзакция §11.3: записи снимка уведомления → статус 4 «Уведомление направлено» + журнал `system` c note «Уведомление №<docnum> направлено, исходящее №<doc_num>»; **каскад EVGA-FR-067а** — записи тех же `ppo_pp` других профилей тоже → 4 (если переход допустим); контрольный срок = `doc_date` + 10 **будних** дней (№3-5) → `its_out.exec_due_time` (ISO-дата); статус заявки → 3 «Отправлен объекту аудита» (=«Исполнен») |
| FR-4 | Идемпотентность: регистрация выполняется один раз (заявка уже в статусе 3 → пропуск) |
| FR-5 | **Вотчер**: фоновая горутина (интервал `EVGA_OUT_WATCH_INTERVAL`, по умолчанию 60s; 0 — выключен) находит уведомления в статусе 5 с `its_out_id`, у которых `its_out.doc_num` непуст, и вызывает Register. Останавливается по graceful shutdown |
| FR-6 | `POST /notices/:id/register {doc_num, doc_date}` — **только админ**: симуляция регистрации канцелярией (заполняет `its_out.doc_num/doc_date` и вызывает Register). Для приёмки на реплике; на проде номер придёт от платформы |
| FR-7 | Карточка уведомления дополняется данными исходящего: `out_num`, `out_date`, `exec_due` (уже частично есть через реестр); UI: кнопка «Создать исходящее» в блоке маршрута при статусе 5 и открытом шаге outgoing |
| FR-8 | Все пишущие операции — за `EVGA_WRITE_ENABLED`; RBAC как в 010 |

## 3. Домен

`AddBusinessDays(from, n)` — +n будних дней (сб/вс пропускаются; праздники не учитываются —
решение №3-5). Юнит-тесты, включая переходы через выходные.

## 4. Критерии приёмки (AT-14)

1. Ответственный создаёт исходящее: `its_out` создан со связями, шаг маршрута закрыт; повторно → 422.
2. Не-исполнитель шага → 403; статус заявки ≠ 5 → 422.
3. Симуляция регистрации (админ): статус заявки → 3; ВСЕ записи снимка → статус 4 со ссылкой-журналом `system`; записи-соседи по `ppo_pp` (другие профили) → тоже 4 (каскад); `exec_due_time` = doc_date + 10 будних.
4. Повторная регистрация → без изменений (идемпотентность).
5. Вотчер: после ручного заполнения `doc_num` в БД (симуляция платформы) уведомление регистрируется автоматически в течение интервала.
6. Записи в статусе 4 недоступны для повторного включения в уведомление (уже покрыто 009) и переводимы аудитором по матрице 4→6/11/2 (уже покрыто 008).

## 5. Вне объёма

Отправка в ШЭП/ЕСЭДО (ждёт учётку), реальная ЭЦП, PDF-вложения (фаза 5), извещения
DELIVERED/EXECUTION/FINISHED (следим только за регистрацией; остальное — после ШЭП).
