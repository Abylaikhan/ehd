# Вопросы аналитику по модулю ОБМ ЕВГА 5-15а

Составлено 06.09.2026. Статус разработки: реестр рисков и простановка статусов реализованы
(на dev-реплике), прод подключён только на чтение. Вопросы сгруппированы по срочности.

## А. Блокируют текущую работу

**А1. Повторные уведомления по одной записи витрины (ТЗ §14.4, OQ-08).**
Может ли одна запись `its_tb_5_15a` входить более чем в одно уведомление?
В данных прода такие случаи уже есть (запись id 14040247 входит в два уведомления),
поэтому строгий уникальный индекс из §14.4 создать невозможно. Варианты:
- а) повторные допустимы (например, после отзыва первого) → частичный индекс без отозванных;
- б) недопустимы → существующие дубли — ошибка, нужно решение о чистке.
Дополнительно: при формировании нового уведомления считать ли запись «уже включённой»,
если её уведомление отозвано (стат. «Отозван»)?

**А2. Условия матрицы статусов (ТЗ §7.2) — подтвердить трактовку.**
Реализовано как условия входа в целевой статус:
- → «Не подтверждено» (2): обязателен комментарий;
- → «Подлежит возмещению» (7): обязательна сумма к возмещению, ≤ суммы записи;
- → «Аудит» (12): обязательно аудиторское мероприятие;
- → «Возмещено» (8): обязательна сумма возмещения; если меньше суммы к возмещению — отказ.
Верно? Если условие относится к другому переходу — указать, к какому.

**А3. Применение изменений БД на прод (ТЗ §14).**
Скрипты готовы (новые поля, вывод статусов из оборота, журнал изменений статусов, индексы).
Нужны: подтверждение заказчика, пишущая учётка БД для приложения, окно применения, бэкап.
До этого прод работает в режиме чтения.

## В. Нужны для фаз «Маршрут / согласование / нумерация»

**В1. Момент подписания ЭЦП (§16 п.5а).** Согласующий подписывает документ на этапе
«Согласование» (отдельного этапа «Подписание» нет) — подтвердить. Или подписание — отдельное
действие / выполняется на стороне ЕСЭДО?

**В2. Семантика задач платформы.** Маршрут ведётся в таблицах `tasks`/`task_hst`, но
справочники `task_types`/`task_statuses` в БД пустые. Какие значения `type_id`/`status_id`
использует текущая система для задач «Согласование» и «Создать исходящее»? (Можем снять
по фактическим задачам, но подтверждение аналитика надёжнее.)

**В3. «Один регион = один департамент ДВГА» (§16 п.9)** — подтвердить. Иначе счётчики
нумерации у департаментов одного региона дадут дублирующиеся номера уведомлений.

**В4. Статусная модель уведомления.** По факту БД статусы ведутся в `its_req_stat`
(«Проект создан», «На согласовании», «На подписании», «Отправлен на доработку», «Отозван»,
«Отправлен объекту аудита»). В ТЗ финальный статус называется «Исполнен» — это
«Отправлен объекту аудита» (stat_id=3)? И используется ли «Отозван» (id=15) как аннулирование
уведомления (связано с А1)?

**В5. Производственный календарь РК (§16 п.7).** Источник данных для расчёта «10 рабочих
дней»: есть ли таблица календаря в БД / внешний сервис / вести справочник у себя?
