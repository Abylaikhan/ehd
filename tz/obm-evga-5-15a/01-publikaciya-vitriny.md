# §5. Этап 1. Публикация данных на витрине

**Исполнитель:** робот публикации. **Периодичность:** по регламенту расчёта профилей риска.

- **EVGA-FR-001.** Расчёт выполняется по каждому активному профилю риска (`its_risk_profile.query_text`), результат загружается в `its_tb_5_15a`.
- **EVGA-FR-002.** При загрузке обязательно заполняются: `its_risk_profile_id`; `its_departments_id` (по региону/КАТО отправителя платежа — точный признак см. OQ-06); `its_risk_status_id = 1` («В работе у ДВГА», стартовый); поля `gu`, `gu_bin`, `ppo_pp`, `paymentdate`, `iin`, `fm`, `nm`, `ft`, `la1`, `amount_part`, `sendername`, `god`, `mes`.
- **EVGA-BR-001.** Без `its_departments_id` запись не видна ни одному аудитору.

## Правило повторной публикации (обязательное)

Слияние по ключу `(ppo_pp, its_risk_profile_id)` — уникальный индекс `its_tb_5_15a_ppo_pp_idx` уже существует.

- **EVGA-FR-003.** Записи нет в витрине → INSERT со статусом 1.
- **EVGA-FR-004.** Запись есть → UPDATE **только расчётных** полей (суммы, реквизиты платежа, данные ГБД ФЛ, признаки). Поля отработки — `its_risk_status_id`, `risk_status_note`, `its_activity_id`, `refund`, `amount_for_vozvrat`, `files`, `audit_resp`, ссылки на уведомление и исходящее — **не изменяются**.
- **EVGA-FR-005.** Запись отсутствует в новом расчёте → не удаляется, проставляется признак неактуальности.
- **EVGA-BR-002.** Полная перезагрузка витрины (`TRUNCATE`/`DELETE + INSERT`) **запрещена**: уничтожит работу аудиторов и разорвёт связи с уведомлениями.
- **EVGA-BR-003.** Приёмка: сценарии AT-02, AT-17 (`11-priyomka.md`).
