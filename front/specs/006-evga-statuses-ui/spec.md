# Спецификация: ОБМ ЕВГА — UI простановки статусов (одиночная и массовая)

- **ID**: 006-evga-statuses-ui
- **Статус**: implemented
- **Требования ТЗ**: EVGA-FR-014/015/018, EVGA-FR-020…023 — `../tz/obm-evga-5-15a/03-statusy.md`;
  backend-контракт — `../back/specs/008-evga-statuses/spec.md`
- **Дата**: 2026-09-06

## 1. Сценарии

- Аудитор отмечает записи чекбоксами в реестре `/evga` («выбрать все на странице» — чекбокс
  шапки DataTable) и нажимает «Сменить статус» → диалог: целевой статус + поля по условиям
  перехода (→2 комментарий обязателен; →7 сумма к возмещению; →8 сумма возмещения;
  →12 аудиторское мероприятие из справочника `activities`).
- После массовой операции — отчёт «Обработано N, отклонено M» с таблицей отклонённых и причин
  (EVGA-FR-023); реестр перезагружается.
- В карточке `/evga/{id}`: кнопка «Сменить статус» (одиночный переход, доступные целевые
  статусы вычисляются по матрице из текущего) и блок «История статусов» из
  `GET /registry/:id/history` (EVGA-FR-018).
- Ошибки 422 (`TRANSITION_NOT_ALLOWED` / `TRANSITION_CONDITION_FAILED`) показываются
  в диалоге текстом backend; 403 `EVGA_READ_ONLY` — предупреждение «модуль в режиме чтения».
- Пишущие контролы скрыты у куратора и не-аудиторов (по `Me.roles`); backend авторизует
  повторно — скрытие не является механизмом безопасности.

## 2. Клиентская матрица (UX-подсказка)

`layers/evga/utils/statusFlow.ts` дублирует матрицу §7.2 для фильтрации целевых статусов
в диалоге и требований к полям. Источник истины — backend; расхождение приводит максимум
к 422 с текстом причины. Покрыта vitest.

## 3. Вне объёма

«Выбрать все по фильтру» (потребует серверную операцию по фильтру — фаза уведомлений),
вложения, подсветка контрольных сроков (фаза 8).
